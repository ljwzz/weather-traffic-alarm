## 阶段 A：标准通知方案

以下为项目默认实施方案，执行时写入规格：

- 用户首次主动启用通勤通知后生效；增加独立启用标记，默认关闭。历史两个摘要字段保留，用于呈现偏好，不能因它们过去默认 `true` 就自动启动新提醒。
- 消费成功且已通过应用校验的本次决策，包括有效的“无需提前”结果；以计划时区安排出发前 5 分钟的一次性通知任务。无出发时间、计划停用、日期不适用或调度应用失败时不发布。
- 普通通知使用独立通勤渠道和绝对出发时间。正文仅使用已有快照；历史天气说明标注评估时间，不将前一晚结果称为实时天气。
- 使用独立 OneTimeWorkRequest 发送及恢复通知，明确为尽力投递。首次投递迟于计划出发时间则不补发；已展示通知在计划到岗时间终止。WorkManager 的初始延迟不是精确执行时间保证，官方依据（2026-09-28 核实）：https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work 。
- “稍后提醒”只将本次通知延后 5 分钟；到岗时间前可再次投递，已过出发时显示绝对计划时间和“已到出发时间”。延后结果达到或超过到岗时间时终止本次提醒并反馈原因。该操作不调用闹钟贪睡，不更改起床或到岗时间。
- “查看通勤”经解锁打开对应计划日期的路线详情，保留返回路径；通知正文可进入原 `decisionId` 的详情。路线配置已变化时明确显示当前配置与原记录的区别，不能把新路线伪装成历史结果。
- 关闭通知总开关、停用／删除计划、撤销有效日期配置或到达终止时间时取消对应任务和通知。用户划掉通知记为本次已结束，同一计划日期的普通刷新不重新弹出；用户主动稍后提醒或重新启用除外。
- 锁屏摘要开启时使用无地点、地址和坐标的公开替代内容；关闭时隐藏锁屏内容。通知最终可见性仍受用户系统设置控制，官方依据（2026-09-28 核实）：https://developer.android.com/develop/ui/compose/notifications 。隐私可见性接口依据：https://developer.android.com/develop/ui/compose/notifications/create-notification 。

## 接口与数据影响

| 拟新增对象／入口 | 契约 |
|---|---|
| `CommuteReminderSnapshot` | 保存 `planId`、`targetDate`、`decisionId`、计划修订、可空日级修订、有效输入指纹、出发／到岗时刻、评估时间、非敏感摘要和当前通知状态 |
| 通知协调器 | `reconcile`／`publish`／`snooze`／`dismiss`／`cancel`，统一处理配置变化、决策成功、恢复及动作回执 |
| 能力模型 | 分别表示通知权限、通勤渠道、锁屏偏好、系统提升能力和设备适配结果，不能用用户勾选代替系统核验 |
| 唯一身份 | 通知以 `planId + targetDate` 复用同一 ID；任务和动作携带 `decisionId` 及修订，旧通知动作不得操作新记录 |
| 持久化 | 新增独立提醒记录及显式 Room 迁移；新增启用标记默认关闭；旧决策缺少显示字段时使用缺省状态，不补当前配置 |

提醒的展示期限与决策首次应用的短有效期分开：只有有效期内被接受的决策可建提醒，次日投递按仍有效的计划日期、修订和已接受快照复核，不因 Provider 缓存过期直接重新应用旧评估。记录所需到岗时间和输入修订须在成功评估时保存。

输入变化取消或替换旧提醒并等待有效新结果；提交和投递前重复校验。N004 尚未交付时，日级修订为空，使用现有日期覆盖值的指纹校验；N004 接入后同时消费日级修订及统一解析结果。这样 N005 不隐含依赖尚不存在的日级接口。

设备重启后在用户解锁时恢复通勤通知任务，并丢弃超出投递窗口的任务；解锁前不读取凭据保护存储或启动该通知 Work。基础及提前闹钟实例继续由既有闹钟协调器管理，通知任务不创建新的响铃实例。

## 阶段 B：胶囊能力前置验证

先形成“平台／系统版本、公开接口、使用条件、权限及开关、实测结果、回退形式”矩阵，再接入适配器。Android Live Updates 要求活动符合进行中、用户发起、时间敏感等条件，OEM 还可增加限制；普通计划提醒不能仅凭有倒计时就认定符合条件。2026-09-28 核实：https://developer.android.com/develop/ui/views/notifications/live-update 。

当前应用场景是否满足提升条件、目标厂商是否提供可用且获准接入的接口，信息不足，无法验证。阶段 B 核对目标设备的官方说明、可执行探针和实际系统表现；条件不成立时保留标准通知，登记阻塞原因，不将自绘应用内胶囊作为系统集成验收。

## 任务拆分与验收

1. 核实标准通知和胶囊前置条件，将本页默认行为同步为规格及状态表。
2. 实现快照、迁移、通知协调器、独立任务和去重／恢复；接通设置与详情／路线导航。
3. 完成标准通知单元及设备矩阵；之后仅对已验证支持的系统接入胶囊适配器。
4. 验证新决策替换、重复动作、重启恢复及多计划隔离，报告两个阶段各自的适用范围与实际结果。

| 场景 | 验收要求 |
|---|---|
| 成功 | 出发前任务在可用窗口内投递；内容来自对应快照；稍后提醒和查看通勤真实可用 |
| 失败 | 权限拒绝、渠道关闭、入口失效和后台延迟均有明确结果；不影响已有响铃 |
| 隐私 | 锁屏开关及系统设置组合正确；详细地点只能解锁后访问 |
| 生命周期 | 停用、删除、到岗终止、用户划掉、配置修改、重启／时间变化后无过期通知复活 |
| 隔离 | 同刻多计划互不覆盖；旧决策动作无副作用；重复点击不创建多个任务 |
| 胶囊 | 支持设备真实呈现；不支持或禁止提升时回退标准通知并记录能力状态 |
